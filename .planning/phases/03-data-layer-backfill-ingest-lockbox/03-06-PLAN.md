<objective>
Ship the two capture-side corrections this phase's own probes discovered are needed to sustain backfill's source precedence and prevent disk exhaustion: `TRADE_SCHEMA` schema_version=2 (adds `exec_type`, replacing the ambiguous `price==0 AND qty==0` NA-placeholder heuristic with an explicit signal) and a `RawArchiveWriter` framing fix (one compressor per file instead of per message, ~1.5x -> ~10x effective compression). Both require exactly one deliberate, checkpointed daemon restart (~3s, `seq` resumes from the sidecar) -- this plan does the code, the offline re-framing of the existing ~21 GB archive, and the gated restart itself.

Purpose: raw is growing ~15 GB/day at weekday rates and would fill the 870 GiB volume in ~2 months, before 3 months of backfill history even exists -- left unfixed, this threatens capture's own continuity, which DATA-02's source-precedence rule depends on ("capture is authoritative for trades on days the archive has not yet published"). The `exec_type` column additionally sharpens Plan 04's DQ NA-filter for all data captured after this restart.
Output: `schema.py` at `SCHEMA_VERSION=2`, `parse_trade` populating `exec_type`, a fixed `RawArchiveWriter`, a re-framed existing archive, and one observed, approved, low-risk daemon restart.
</objective>

```
SCHEMA_VERSION: int = 1
TRADE_SCHEMA: dict[str, pl.DataType]  # symbol, stream, trade_id, etime, event_time, price, qty, is_buyer_maker, seq, rtime, source, schema_version
```

From `mvp/data/capture/rotation.py`: `write_partition_atomic(rows: list[dict], schema: dict, data_root: Path, symbol: str, stream: str)` builds `pl.DataFrame(rows, schema=TRADE_SCHEMA)` -- this is why the schema bump and `parse_trade`'s `exec_type` population MUST land in the same task/commit: a `TRADE_SCHEMA` with `exec_type` but rows missing that key raises at `pl.DataFrame(rows, schema=...)` construction time inside the running daemon's `flush_stream`, which is caught as an `OSError`-only try/except in `rotation.consume` -- a `ValueError`/schema mismatch would NOT be caught there and would crash the consumer task, growing the in-memory queue unboundedly. Ship schema + parser together, verified green against `tests/capture` BEFORE the restart task even begins.

RawArchiveWriter lives in `mvp/data/capture/ws_client.py` (not yet read this session -- read it first as this task's own `<read_first>`). Current defect (measured, PROBE-RESULTS.md section 4): a fresh `ZstdCompressor().stream_writer` is constructed per message. Fix shape: one long-lived compressor opened once per raw archive file, `flush(zstandard.FLUSH_BLOCK)` after each message (durability -- readable up to the last flushed block even if the process dies mid-file), `flush(zstandard.FLUSH_FRAME)` every N messages or seconds (bounds how much of the tail a crash can lose, since `FLUSH_BLOCK` alone does not close a decodable frame boundary for every possible reader).
