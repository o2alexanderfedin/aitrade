<objective>
Build the lockbox quarantine mechanism: physical path separation (`lake/lockbox/`, a sibling root the default loader never constructs a path into), a POSIX `chmod 0000` second barrier, a one-look unlock-token API whose consumption check queries MLflow first (the durable record) before the git-committed JSON file (which a same-uid `git checkout --` can silently revert), and a CI guardrail proving no agent-run script references the lockbox path outside the one audited module. Not populated with real data this phase -- the red-proof quarantines a synthetic fixture segment.

Purpose: DATA-08, and RP-3 (the phase's subtlest red-proof -- the containment test must fail when the chmod line is removed, proving it tests reachability and not merely that a path string is absent). Honestly scoped: this delivers accident-proofing plus an audit trail against a same-uid but non-adversarial actor; a determined same-uid agent can always `chmod` the barrier back, which is stated plainly rather than oversold, per CONTEXT.md's own instruction.
Output: `data/lockbox.py`, `tools/check_lockbox_containment.py` (wired into both CI callers), `data/lockbox_POLICY.md`, a lockbox section in `CLAUDE.md`, a new DON'T in `spec.md`, and RP-3 observed and transcribed.
</objective>

Create `mvp/data/lockbox.py`:
- `LockboxTokenError(ValueError)`.
- `_token_path(token_id: str) -> Path` -- `LAKE_REGISTRY_ROOT / "lockbox_tokens" / f"{token_id}.json"` (imported from `data.lake_paths`; the correction from CONTEXT's literal `lake/lockbox/tokens/` path, documented above).
- `issue_token(token_id: str, segment_manifest_id: str, purpose: str, gate: str, requested_by: str) -> dict` -- writes a new token JSON (`created_at` = now, `consumed_at` = `None`, `mlflow_run_id` = `None`) atomically to `_token_path`, git-committed by the caller's normal commit flow (this function only writes the working-tree file). Refuses to overwrite an existing `token_id`.
- `_mlflow_has_consumed(token_id: str, tracking_root: str) -> bool` -- queries `MlflowClient().search_runs(...)` (never the pandas-returning `mlflow.search_runs()`, per spec.md's existing DONT) filtered to `tags.lockbox_token_id = '<token_id>'`; returns `True` if any run is found, `False` if the query succeeds and finds none. **Any exception the query itself raises (unreachable tracking root, empty/reset/corrupted tracking DB) propagates unmodified -- this function never catches a query error and returns `False`.** This is deliberate: `False` means "asked MLflow and it said no", not "could not ask MLflow" -- collapsing those two into one `False` would mean pointing `open_lockbox` at a reset or unreachable tracking root silently re-arms every previously consumed token, defeating the one thing this function exists to do (RESEARCH.md Pitfall 4: MLflow is supposed to be the DURABLE check precisely because the JSON stamp is revertible; an error here must be at least as conservative as "already consumed", never treated as "not consumed"). This is the DURABLE check, consulted FIRST.
- `open_lockbox(token_id: str, purpose: str, requested_by: str, tracking_root: str, lake_root: Path | None = None) -> pl.DataFrame` -- order of operations, exactly: (1) read the token file, raise `LockboxTokenError` if absent; (2) call `_mlflow_has_consumed` FIRST -- raise `LockboxTokenError("token already consumed (MLflow record)")` if `True` (catching the case where the JSON's `consumed_at` was silently reverted by a same-uid `git checkout --`, T-03-08), and let any exception `_mlflow_has_consumed` itself raises (query error) propagate straight out of `open_lockbox` UNCAUGHT -- `open_lockbox` does not wrap this call in a `try/except` that could turn a query failure into an implicit "proceed" (a caller who wants a friendlier message can catch the underlying MLflow exception itself; `open_lockbox`'s own contract is "refuse unless the durable check positively says not-consumed"); (3) check the JSON's own `consumed_at` field -- raise if already set (belt-and-suspenders, cheaper check, still useful when MLflow is unreachable); (4) **stamp `consumed_at` in the JSON atomically, BEFORE returning any rows** (Pitfall 4's documented safer-failure-direction: a crash between steps 4 and 5 leaves the token looking burned, not silently reusable); (5) call `start_tracked_run(tracking_root, tags={**the 8 mandatory keys as described in this plan's interfaces block, "lockbox_access": "true", "lockbox_token_id": token_id, "lockbox_purpose": purpose}, experiment_name="lockbox_access")`, and inside that run, resolve the segment's manifest (reusing `store.resolve_manifest`, which still verifies partition hashes even for a lockbox-tier manifest -- immutability applies here too) and read the partitions from `lockbox/`-rooted paths -- **this function is the only place in the entire codebase permitted to join a path under `lockbox/`**; (6) write the run's `run_id` back into the token JSON's `mlflow_run_id` field; (7) return the loaded DataFrame.
