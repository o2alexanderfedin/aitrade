  <action>
Create `mvp/data/backfill/downloader.py`: a `ThreadPoolExecutor`-based orchestrator (4-8 workers -- Claude's Discretion per CONTEXT.md) that, given a date range, determines for each `(year, month)` in `2026-06, 2026-07, 2026-08` whether to use the monthly zip (present) and for each date from `2026-09-01` onward uses the daily zip, reusing `BackfillClient`/`list_month`/`download_and_verify`/`extract_expected_member` from Plan 01 without duplicating any of their logic. **Monthly files are never read as one in-memory `pl.DataFrame`**: after `extract_expected_member` extracts the monthly CSV to the validated `backfill_staging_root()`, read it via `pl.scan_csv(path, schema_overrides=...)` and either `.sink_parquet(...)` per-day-filtered output or an explicit per-day `.filter(...).collect()` loop that processes one UTC day's rows at a time before discarding them -- the measured 3.16x RSS multiplier on a 42MB daily file extrapolates to ~23GB peak RSS for a naively-loaded monthly file on a 32GiB machine already running the capture daemon, which this design avoids by construction (T-03-06: Denial of Service, mitigated by never holding the full decompressed CSV in memory as one frame).

For each UTC date in the range, after the day's CSV is staged (daily path) or filtered out of the monthly scan (monthly path), the orchestrator completes what Plan 01 Task 3 did manually for the single 2026-09-12 slice: `normalize_archive_trades` (Plan 01, using the day's unit-registry entry) then `write_raw_partition` (Plan 01) to produce `lake_root()/raw/.../date=<D>/`. **This per-date step must skip-and-continue, not crash, on a day whose raw partition already exists**: `write_raw_partition` already refuses (raises `FileExistsError`) rather than overwriting (Plan 01's immutability-by-construction design) -- the orchestrator catches exactly that exception per date, logs the date as already-present, and proceeds to the next date, mirroring `build_curated_day`'s own idempotent-range idiom (Task 2, below) rather than letting one already-ingested day abort the entire range. This is what makes the full-window run genuinely re-runnable after an interruption (CONTEXT.md's own requirement: the downloader is "idempotent per (symbol, date), and is re-runnable every day") at the RAW-tier level, not just at `BackfillClient`'s download/checksum level.

Run the downloader for real across the full `2026-06-01 -> yesterday` window. Record in the SUMMARY: total files downloaded, total bytes, every checksum verdict (pass/fail count), and -- for the first monthly file processed -- peak RSS measured via `/usr/bin/time -l` (or equivalent), compared against the ~23GB naive-approach estimate this design avoids (Manual-Only Verification per 03-VALIDATION.md: "Monthly-zip ingest does not OOM alongside the live capture daemon").
  </action>

  <done>The downloader's monthly-vs-daily branch selection is unit-tested against a mocked date range spanning both regimes; a test asserts that re-running the per-date normalize+raw-write step against an already-written date is a no-op (skip-and-continue, not `FileExistsError` propagating out of the loop) while an adjacent not-yet-written date in the same range still gets processed; the real full-window backfill run is complete, its file count/bytes/checksum verdicts recorded in the SUMMARY, and the first monthly file's peak RSS is recorded and confirmed well below a naive-load estimate.</done>
