**Structural confinement to the OOF blocks.** The function takes the train cache and the five OOF block names and has **no parameter through which `val` could be named**; assert every segment name it handles matches `oof_block_<int>` and raise otherwise. D-07-04 is then a property of the signature rather than of the caller's discipline.

**The loop.** For each of the 17 configs, for each of the 5 blocks:
- training rows = `harness.kfold.training_rows_for_block(train_frame, blocks, j, purge_ns=..., embargo_ns=...)` with `purge_ns`/`embargo_ns` read from the segment manifest body, not recomputed.
- fit through the Trainer protocol, with `FitInputs` naming the train cache path and, where a row subset is needed, a positional Boolean `keep` mask Parquet of exactly the cache's height (no join: polars' join order is unspecified).
- score the block's own materialized rows (one look each, already spent by `materialize_once`), computing `models.metrics.forecast_metrics` STREAMING and persisting only the scalars. **No OOF prediction table is stored** (D-07-15): storing four estimators' tables on every segment approaches a gigabyte for no downstream reader, which is exactly the massive-data production this session is told to avoid.
- evaluate `gates.gate_forecast` per block.

**The handoff artifact, because `--select` and `--freeze` are different processes separated by a commit.** `SweepResult` is in-memory; plan 07-10 runs `--select`, commits, then runs `--freeze`, so nothing in memory survives the gap — and an executor would discover that AFTER five looks are spent, facing a choice between improvising a format and re-running 85 fits over ~40M rows. `run_oof_sweep` therefore also WRITES `selection.json` into the same tracking-root-keyed scratch directory the frame cache uses:
`cache_root/sha256(resolved tracking_root)[:16]/<segment_manifest_id>/selection.json`, carrying `segment_manifest_id`, `normalization_manifest_id`, `winner_grid_index`, the winner's `model_class` and full `hyperparameters`, the per-block metrics for every config, the eligible-config count, `n_configs`, and the five OOF `look_run_ids` observed at the end of the sweep (run 3 re-queries them live and asserts the live set COVERS these — a recorded id missing from the query means the store was moved or pruned, which is worth failing over). **Write it with the same `_atomic_write_json` the frame cache in that directory uses** — copied, with a docstring saying so, per the repo's cross-module helper policy. It is the artifact carrying five looks' worth of work across a commit boundary; a half-written one is the worst possible outcome. Keying it by tracking root is the same defence the frame cache uses: a selection made against a scratch store can never be mistaken for one made against the real store. Its reader refuses when the file is absent, or when either id inside it disagrees with the live manifests it is being applied to.

**The selection rule, stated in code** (CONTEXT.md leaves the criterion to Claude's discretion; this is the choice, and it must be documented in the module docstring so Phase 8's cross-class protocol inherits it rather than reinventing it):
1. A config is ELIGIBLE only if `gate_forecast` passes on ALL FIVE blocks. One bad block disqualifies; a mean that hides a failing fold is how an unstable model wins.
2. Among eligible configs, rank by the MEAN of `rank_ic_non_tied` across the five blocks.
3. Tie-break on the mean `r2_vs_mean`; break a remaining tie deterministically by the config's position in the grid, so the winner is reproducible.
4. Report the per-block spread (min, max, standard deviation) of the winner's IC alongside the mean — Phase 8's FCST-05 wants exactly this shape, and the one-calendar-day blocks make it directly interpretable as per-day metrics.
5. If NO config is eligible, return a result that says so explicitly. That is a real outcome, not an error to paper over, and the caller must not fall back to "best available".

**Every ineligible config is recorded before selection moves on** (D-07-20): `record_negative_result` with a `reason` naming the failing block and the failing statistic, and a `config_fingerprint` over the same recipe fields `predictor_id` uses. A failed config that leaves no trace is a config the project will pay to re-try. Call `warn_if_already_negative` first so a re-run does not silently duplicate records. Keep each `reason` under the length `record_negative_result` refuses.

**No MLflow run of the sweep's own may be open** — `record_negative_result` opens its own run per record and cannot nest (D-07-30).

Log per-config wall clock. If a config's fit exceeds a stated budget on real data, that is a finding to report, not a reason to shrink the grid.
