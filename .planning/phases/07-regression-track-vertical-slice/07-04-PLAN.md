Create `mvp/models/frozen.py`. It imports numpy, json, hashlib, pathlib and `models.predictor_id` — **and never sklearn**. State that in the module docstring as the contract that makes D-07-17's test possible.

`FrozenPredictorError(ValueError)` — dedicated class, with a docstring stating why a bare `ValueError` would let a test pass for the wrong reason (it would also match unrelated raises in this module and in `predictor_id`), exactly as `ErrataManifestError`'s docstring does.

`FrozenLinearPredictor` — a frozen dataclass satisfying the `FrozenPredictor` Protocol, holding:
- `model_class: str` (for example `"sklearn.Ridge"`)
- `design` — **a `@property`, NOT a field**: `return "poly2" if self.hyperparameters.get("degree") == 2 else "linear"`. A field could disagree with the recipe, and a body carrying `design="poly2"`, nine coefficients and NO `degree` key would pass every check while hashing a recipe identical to plain Ridge at the same alpha — the collision, reopened one level down. A property cannot disagree with what it is computed from. `to_artifact()` may still EMIT `design` for readability; `read_frozen_predictor` then asserts the emitted value equals the derived one as a fourth refusal.
  What the property means: `"linear"` or `"poly2"`. **It is load-bearing, and it DERIVES from the hashed recipe rather than shadowing it.** Three of D-07-08's four estimators have 3 coefficients; the fourth is Ridge on `PolynomialFeatures(degree=2, include_bias=False)` and has 9 plus an intercept. Without `design`, the sklearn-free re-evaluation cannot know how to rebuild the design matrix.
  **Derive it: `design = "poly2" if hyperparameters.get("degree") == 2 else "linear"`, and assert the two agree.** `predictor_id` hashes exactly D-07-14's five fields and `design` is not one of them, so a `design` carried only on the dataclass would collide: the counted grid runs Ridge at alpha {1e-6, 1e-3, 1.0, 100.0} and Ridge+poly2 at alpha {1e-3, 1.0, 100.0}, three SHARED alphas at identical `model_class`, seed, code hash and normalisation id. Three pairs of configs would share one `predictor_id`, which breaks the negative-log deduplication (D-07-20 loses up to three traces) and lets a stored table's `predictor=<first 16 chars>` path name a config that never produced it. Putting `degree` in `hyperparameters` puts it inside the hash, where it belongs.
- `feature_names: tuple[str, ...]` — always the THREE INPUT names `("imb_top", "ofi", "trade_flow")` in that pinned order, for both designs. The 9 expanded columns are derived, never named here.
- `coef: tuple[float, ...]` (3 entries for `linear`, 9 for `poly2`), `intercept: float`
- `normalization_manifest_id: str`, `seed: int`, `code_hash: str`, `hyperparameters: Mapping[str, Any]`
- `train_target_mean: float` — the mean of `ret_10s_mid` over the rows this model was FITTED on. It is in the body, not the recipe, so it changes `manifest_id` and never `predictor_id`. It exists because `models.metrics`' zero-skill control column is "a constant predictor AT THE TRAIN MEAN"; `mode="val"` never reads the train frame, so without this field the only mean to hand is the evaluation set's, and logging that under a key saying "train" would make the control column a different, weaker statistic than the one the human checkpoint asks the developer to read.
- `predictor_id` property, re-derived from the recipe via `models.predictor_id`, never stored twice as a source of truth
- `__post_init__` asserting `len(coef)` against the DERIVED `design`: 3 for `"linear"`, 9 for `"poly2"`, raising `FrozenPredictorError` naming both numbers and the `degree` value it derived from. A body whose design and coefficient count disagree can never predict correctly, and this is the cheapest place to find out.
- `n_rows_fitted: int`, `n_rows_dropped: int` — **body fields with exactly `train_target_mean`'s status**: on the dataclass, emitted by `to_artifact()`, and EXCLUDED from the hashed recipe. They must not be hyperparameters (inside the recipe they would give each OOF block's fit of the same config a different `predictor_id`, inverting what D-07-22 needs: two runs of the same recipe must share a `predictor_id` so that differing coefficients show up as differing `manifest_id`s), and they must not be a second return value either (`Trainer.fit(...) -> FrozenPredictor` returns exactly ONE object; a tuple would fail the runtime conformance check and break the interface Phase 8 has to extend without editing).

`predict(features)` — `(n, 3)` already-normalised float64 in, `(n,)` float64 out, in the target's unit (a 10s return). For `design == "poly2"` expand to 9 columns in **exactly** sklearn's `PolynomialFeatures(degree=2, include_bias=False)` order: `(x0, x1, x2, x0*x0, x0*x1, x0*x2, x1*x1, x1*x2, x2*x2)` — 3 linear, then the degree-2 terms in that upper-triangular sweep. Measured: that expansion is exactly 9 columns for 3 inputs, not 6 and not 10. Then `intercept + X_design @ coef`. Refuse a wrong column count and a non-float64 dtype with `FrozenPredictorError` naming both the expected and the received shape; refuse silently-NaN input by leaving NaN in the output (the caller's mask is the control), and say so in the docstring.

`to_artifact() -> dict` — a JSON-able body: `model_class`, `design` (emitted from the property, for readability), `feature_names` (list), `coef` (list of plain `float`), `intercept`, `normalization_manifest_id`, `seed`, `code_hash`, `hyperparameters`, `train_target_mean`, `n_rows_fitted`, `n_rows_dropped`, `predictor_id`, `schema_version`. Coerce every numeric to a Python `float`/`int`: `json.dumps` raises `TypeError` on a numpy scalar, and a mid-sweep TypeError is a bad place to learn that.

`predictor_registry_path(registry_root, manifest_id) -> Path` = `registry_root / "predictors" / f"{manifest_id}.json"`, flat, mirroring `errata_manifest_path`'s shape, with the same "single source of truth for this body's on-disk path" docstring.

`write_frozen_predictor(predictor, *, registry_root) -> dict` — build the artifact body, compute `manifest_id = compute_manifest_id(body)` (the canonicaliser drops the `manifest_id` key and sorts keys, so the id covers the coefficients too), insert it, write atomically with a COPIED `_atomic_write_json` whose docstring says it is copied from `data.store` and why. Refuse to overwrite an existing path.

`read_frozen_predictor(manifest_id, *, registry_root) -> FrozenLinearPredictor` — three refusals, all raising `FrozenPredictorError`:
1. named-but-missing FAILS CLOSED — never a default, never `None`;
2. the self-hash is recomputed and compared against BOTH the id the caller passed AND the body's own `manifest_id` field, so a hand-edited body kept "helpfully in sync" is caught exactly as a stale one is;
3. `predictor_id` is RE-DERIVED from the body's recipe fields (`model_class`, `hyperparameters`, `seed`, `code_hash`, `normalization_manifest_id`) and cross-checked against the stored `predictor_id`.
4. The body's emitted `design` is cross-checked against the value derived from `hyperparameters["degree"]`, and `len(coef)` against that derived design (3 or 9). A body claiming `poly2` while carrying no `degree` key is refused here rather than predicting plausibly with a colliding recipe.
Docstring must state why the body carries both ids (D-07-22): two runs of the SAME recipe that disagree on coefficients yield the same `predictor_id` under different `manifest_id`s, which makes the determinism claim checkable as DATA and not only as a test.

Finally, wire `models.protocol.predictor_from_artifact` to return a `FrozenLinearPredictor` for the model classes this phase produces, with the import done INSIDE the function body to avoid an import cycle, and a comment saying Phase 8 extends the dispatch by adding an entry rather than editing the Protocol.

Write NO body under `mvp/data/lake_registry/predictors/` in this plan (hard constraint 3).
