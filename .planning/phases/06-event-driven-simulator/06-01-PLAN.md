<objective>
Land the schema migration 06-RESEARCH.md's Critical Finding 1 forced and 06-CONTEXT.md's D-06-17/18 chose: the feature tier gains `bid_price`/`ask_price` as bookkeeping columns (the kernel already carries them in state), `FEATURE_SCHEMA_VERSION` becomes 2, and the write-once tier gains a version-scoped part-file identity so a v2 rebuild can coexist with a v1 partition already on disk for the same date without touching it. A parallel gap this plan also closes, found by reading `data/dq/report.py` directly rather than assumed: the DQ-report generator resolves only the by-date pointer's CURRENT manifest when it rebuilds a date's `report.parquet`, and `write_report` overwrites that file wholesale — so, unfixed, issuing a v2 manifest and regenerating the report would silently drop v1's features-tier DQ row and turn `load_features(v1_id, ...)` into a `DQPauseError` even though nothing touched v1's manifest or partition bytes. This plan is entirely fixture-driven (`tmp_path` lake/registry roots); it writes no real lake data. Plan 06-04 exercises this code on the real 7-day pool.

Purpose: without this plan, `mvp/sim/`'s D-06-01 (`bid_ticks`/`ask_ticks` from the accessor's frame) has no honest source column, and D-06-18's write-once refusal blocks the rebuild outright.
Output: `FEATURE_SCHEMA_VERSION=2` code path, a version-scoped write-once mechanism, and a DQ-report generator that judges every manifest a date has ever had, not only its current one.
</objective>
