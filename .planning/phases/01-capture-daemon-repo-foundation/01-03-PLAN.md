Redundant capture daemon records Binance Swap L1 + trades to Parquet continuously, surviving a
single connection drop without data loss — this plan is where "redundant" and "without data loss"
stop being aspirational and become true.

<objective>
Add the second, staggered websocket connection and the dedup + gap-ledger stages that make the
already-running single-connection daemon (Plan 02) actually redundant: a drop on either
connection must not lose a row the other connection delivered, and every real outage must be
recorded, not silently absorbed or silently missed.

Purpose: ROADMAP.md's Phase 1 success criterion #1 ("surviving a single connection drop without
data loss") and #2 ("gap ledger records every capture outage") are both scoped to this plan.
Output: `mvp/data/capture/{dedup,gap_ledger}.py`, `rotation.py`/`daemon.py` extended with the
second connection and merge/dedup/gap stages, and a running two-connection daemon confirmed by a
human to tolerate a scripted drop.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Two independent exchange connections -> one merged stream | The dedup stage is now a security-relevant correctness boundary, not just a data-quality nicety: a wrong dedup design silently reintroduces the exact data loss redundancy exists to prevent |
| Long-running dedup state -> host memory | The seen-set is the one new unbounded-growth risk introduced in this plan |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|------------------|
| T-1-12 | Denial of Service (memory) | `mvp/data/capture/dedup.py` | mitigate | `BoundedDedup` evicts entries older than `ttl_seconds` on every call — the seen-set's steady-state size is bounded by one TTL window of unique keys, not by total run length |
| T-1-13 | Repudiation / Tampering (silent data loss) | `mvp/data/capture/dedup.py` design choice | mitigate | Explicitly rejects a high-water-mark dedup design (documented in the module docstring and proven by `test_dedup.py`'s late-arrival case) because it would silently drop legitimately-late deliveries from the redundant connection — the one failure mode redundancy exists to prevent |
| T-1-14 | Denial of Service (availability, coincident disconnect) | `mvp/data/capture/daemon.py` connection stagger | mitigate | The two connections are started `--stagger-seconds` apart specifically so Binance's ~24h forced disconnect does not hit both connections in the same window |
