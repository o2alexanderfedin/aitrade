<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Human editor -> features.toml/labels.toml | A human hand-edits the catalogue source of truth; CI/pre-commit is the only enforcement of its schema and drift rules |
| git history -> check_spec_diff.py | The definition-drift check trusts `git show <ref>:path` output as the "old" state; a rewritten/rebased history could defeat it |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-------------------|
| T-2-08 | Tampering | mvp/spec/catalogue.py | mitigate | Required-key set validation on every load; CatalogueError on any missing key, so a malformed entry cannot silently pass through as a valid feature/label |
| T-2-09 | Tampering | mvp/tools/check_spec_diff.py | accept | `--base-ref HEAD~1` can be defeated by an interactive rebase that drops the "old" commit before CI runs; accepted because this project's git-flow (feature branches, PR review) makes a deliberate history rewrite to hide a definition change an unlikely, high-effort attack for a single-developer research repo, not worth adding signed-commit infrastructure for at Stage 0 |
| T-2-10 | Information Disclosure | mvp/spec.md | accept | The spec is a plaintext, committed, project-internal document with no secrets by design (conventions and catalogue entries only) — no mitigation needed beyond normal repo access control |
</threat_model>
